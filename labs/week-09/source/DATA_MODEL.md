# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

## 1. ภาพรวม
**แผนภาพความสัมพันธ์**<br>
`users (1)` ────── `(N)requests`

**ความสัมพันธ์** เป็นแบบ **One-to-Many** เพราะผู้ใช้ 1 คน สามารถแจ้งคำร้องได้หลายรายการ แต่ 1 คำร้องจะเป็นของคนแจ้งเพียงคนเดียวเท่านั้น

---

## 2. ทำไมต้องแยกเป็น 2 ตาราง

เหตุผลที่ต้องแยก `users` ออกจาก `requests` คือเพื่อป้องกันปัญหาที่ แก้ข้อมูลที่เดียวไม่พอ ต้องแก้หลายที่ และลดความซ้ำซ้อนของข้อมูล
- เช่น หากเก็บชื่อไว้ในตารางคำร้องทุกอัน ถ้าสมชายแจ้งคำร้องไว้ 50 รายการ แล้ววันหนึ่งเขาขอเปลี่ยนชื่อเป็น "สมคิด ใจงาม" ก็จะต้องตามไปเปลี่ยนข้อมูลถึง 50 ที่ ถ้าแก้ไม่ครบ ข้อมูลจะเกิดความขัดแย้งกัน บางคำร้องเป็นชื่อเก่า บางคำร้องเป็นชื่อใหม่
* การแยกเป็น 2 ตารางแล้วใช้ FK ชี้มาหา ID ผู้ใช้ จะทำให้เก็บชื่อไว้ที่เดียว เมื่อเปลี่ยนชื่อที่ตาราง `users` เพียงครั้งเดียว ข้อมูลในคำร้องทั้งหมดก็จะถูกต้องตามไปด้วยทันที

---

## 3. รายละเอียดตาราง

### ตาราง `users`
| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด (Constraint) | เหตุผลที่เลือก |
|---|---|---|---|
| id | INTEGER | PRIMARY KEY | เป็น ID ตัวเลขที่ระบบสร้างให้ ไม่มีการเปลี่ยนแปลง และไม่ซ้ำกัน |
| name | TEXT | NOT NULL | ผู้ใช้ทุกคนต้องมีชื่อและห้ามเว้นว่าง |
| department | TEXT | NOT NULL | ต้องระบุ department และห้ามเว้นว่าง |
| email | TEXT | NOT NULL , UNIQUE | อีเมลจำเป็นสำหรับการติดต่อ และใช้ UNIQUE เพื่อไม่ให้สมัครซ้ำ และห้ามเว้นว่าง |

### ตาราง `requests`
| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด (Constraint) | เหตุผลที่เลือก |
|---|---|---|---|
| id | TEXT | PRIMARY KEY | ใช้เป็นรหัสประจำคำขอแต่ละรายการ ต้องไม่ซ้ำกันและไม่เป็น NULL |
| requester_id | INTEGER | NOT NULL, FOREIGN KEY | ใช้เชื่อมโยงกับตาราง users เพื่อระบุตัวผู้แจ้ง โดยใช้ตัวเลข ID และห้ามเว้นว่าง |
| request_type | TEXT | NOT NULL, CHECK | ใช้เก็บประเภทของคำขอ และจำกัดให้เลือกได้เฉพาะ แจ้งซ่อม, บริการบัญชีผู้ใช้, ขอใช้อุปกรณ์, อื่น ๆ และห้ามเว้นว่าง |
| location | TEXT | NOT NULL | ใช้ระบุสถานที่ที่เกี่ยวข้องกับคำขอ เช่น ห้องเรียน ห้องปฏิบัติการ หรือสำนักงาน และต้องมีข้อมูล และห้ามเว้นว่าง |
| details | TEXT | NOT NULL | ใช้เก็บรายละเอียดเพิ่มเติมของคำขอ เพื่อให้ทราบปัญหาหรือความต้องการอย่างชัดเจน และต้องมีข้อมูล |
| priority | TEXT | NOT NULL, DEFAULT 'normal', CHECK | ใช้ระบุความเร่งด่วนของคำขอ โดยกำหนดค่าเริ่มต้นเป็น normal และอนุญาตเฉพาะ normal หรือ urgent |
| status | TEXT | NOT NULL, DEFAULT 'pending', CHECK | ใช้ติดตามสถานะของคำขอ โดยเริ่มต้นเป็น pending และอนุญาตเฉพาะ pending, in-progress, completed เท่านั้น |
| created_at | TEXT | NOT NULL, DEFAULT CURRENT_TIMESTAMP | ใช้เก็บวันและเวลาที่สร้างคำขอ โดยระบบกำหนดเวลาให้อัตโนมัติเมื่อเพิ่มข้อมูลใหม่ |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

**ทำไม `users.id` กับ `requests.id` ใช้ชนิดต่างกัน** <br>
- `users.id` ใช้ INTEGER เพราะเป็นหมายเลขประจำตัวผู้ใช้ เช่น 1 , 2 , 3 ซึ่งเหมาะกับการใช้เป็น Foreign Key และอ้างอิงผู้ใช้ได้ง่าย ส่วน `requests.id` ใช้ TEXT เพราะรหัสคำขออาจต้องการรูปแบบที่อ่านง่ายหรือสร้างเป็นรหัสเฉพาะ เช่น REQ-001, REQ-002

**ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว** 
- CHECK constraint ทำหน้าที่เป็น กฎบังคับที่ระดับ Database เพื่อป้องกันข้อมูลผิดพลาด แม้ว่าข้อมูลจะถูกเพิ่มโดยช่องทางอื่นที่ไม่ได้ผ่าน API

## 5. ตัวอย่างการใช้ JOIN

```
SELECT r.id , u.name , r.request_type , r.details , r.status
FROM requests r
JOIN users u 
ON u.id = r.requester_id;
```
**ผลลัพธ์ที่ได้** <br>
| id | name | request_type | details | status |
|---|---|---|---|---|
| REQ-001 | สมชาย ใจดี | แจ้งซ่อม | เครื่องปรับอากาศไม่ทำงาน | pending |
| REQ-002 | สุภาวดี รักเรียน | บริการบัญชีผู้ใช้ |  เข้าสู่ระบบห้องปฏิบัติการไม่ได้ | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ | ขอใช้อุปกรณ์ | ขอยืมโปรเจกเตอร์ | completed |
---

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

จากการทดสอบ JOIN ข้อมูล 2 ตารางเข้าด้วยกัน และตั้งชื่อคอลัมน์ใหม่ด้วย AS สังเกตได้ว่า ผลลัพธ์ที่ดึงออกมาจากฐานข้อมูล มีหน้าตาเหมือนกับโครงสร้างข้อมูล JSON ที่ API ส่งกลับไปให้ React
